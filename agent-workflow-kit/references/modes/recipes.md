### Mode: recipes

<!-- opt-in-capability: none — an inspection surface that configures nothing -->

Read-only **orchestration advisor**. Answers *"how should I compose the carriers of a step — the optional execution-backends, the full-tool executor and the no-shell author vehicle — into plan → execute → review here, and which recipe fits?"* It **never writes, never commits, never runs a subscription CLI, and never executes a recipe** — the orchestrator (you) runs the chosen recipe through the bridge skills or the vehicle of the slot's role and makes the single commit; a backend or a subagent is advisory or delegated, never autonomous.

The five recipes (defined over each bridge's `provides` roles — `codex`: execute + review; `agy`: review + probe — plus the `carry` role the placed **executor vehicle** provides and the `author` role the placed **author vehicle** provides), canonical narrative in the **installed engine** (`references/orchestration.md`):

- **Solo** — you plan, execute, and self-review; no backend (always available; the floor).
- **Reviewed** — you execute; **one** backend reviews the result (advisory). Prefers `codex` when both are ready (`agy` carries a standing health caveat).
- **Council** — **both** backends review independently; you synthesize the two opinions.
- **Delegated** — you hand a **bounded** execution sub-task to a backend (`codex exec`), then review the returned diff and commit.
- **Subagent** — a **frontier subagent** from the vehicle of the slot's role carries a bounded slice. Carry slots ride the full-tool executor (`.claude/agents/executor.md`) for a file-disjoint execution or write-capable routine slice, or one prompt the orchestrator wrote from one ledger row, run inside its Files (`task.execute`; `task.author` dispatches no slice: the orchestrator writes each row's prompt itself); you run its suites yourself. Author slots ride the no-shell author vehicle (`.claude/agents/author.md`) for a plan/contract brief, a round's fold or an epic brief; you review the draft as your own. You make the commit. Neither vehicle is a **review backend** or a **bridge substitute**, and neither is **told to commit**; a carry slot **degrades to Solo** on a `missing` or `unusable` executor, and an author slot on any author state but `placed`, each naming its vehicle and the reason. Readiness here is the **vehicle FILE, never the host** — a **Claude Code lane**, like the `agents` writer itself: on a host that cannot dispatch the vehicle, the rendered dispatch form is an instruction you follow by hand and report as such, never as a subagent dispatch.

1. Run **`node ${CLAUDE_SKILL_DIR}/tools/recipes.mjs`** (the read-only planner; `--json` for the structured form). It runs the backend detector, lists the five recipes (a Subagent plan per role), and prints — for the current environment — a **per-recipe dispatch plan that degrades with a stated reason** when a carrier isn't `ready` (Council → Reviewed → Solo; Delegated → Solo; Subagent → Solo when the carry slot's executor is `missing`/`unusable` or the author slot's author vehicle is not `placed`), plus advisory **quota/health notes** (each bridge runs the host posture the user set — a weaker model is the user's bridge setting, never a per-call choice; Council spends two backends' quota; `agy` may stall on substantive prompts — Issue-001, prefer `codex`).
2. **Offer the choice** via **`AskUserQuestion` where your agent supports it** (`AskUserQuestion` in Claude Code) — one option per recipe, the `recommendRecipe` choice listed **first** — otherwise in prose. Then, for a named slot, print `planRecipe(chosenId, detection, slotRole(activity, slot))`, where `chosenId` is the recipe id (the per-stage dispatch + degradation reasons + quota/health notes), so the user sees exactly what running it entails; when Subagent is chosen with no slot named, print both role-specific plans, as step 1 does.
3. **Availability = `readiness === ready`, full stop.** Every other readiness supplies the human reason (needs-skill → "not installed — `/agent-workflow-kit setup`"; needs-cli → "install the CLI"; needs-credentials → "log in"; degraded → "wrapper not on PATH — `/agent-workflow-kit setup`"). This is set-up state only — **never** a claim that a backend's service is responsive (the detector cannot observe a runtime stall; `agy`'s Issue-001 is a *standing advisory*, not a readiness signal).

**The activities and their slots.** One registry (`tools/carriers.mjs`, re-exported by `recipes.mjs`) names **six** activities and their typed slots: `plan-authoring` → `author`, `fold`, `review`; `plan-execution` → `execute`, `review`; `routine` → `carrier`, `parallel`; `feedback-triage` → `review`; `epic` → `author`, `review`; `task` → `author`, `execute`. Each slot's accepted values follow its TYPE — `review` (including `epic.review`) accepts `solo|reviewed|council`; `execute` (including `task.author` and `task.execute`) accepts `solo|delegated|subagent`; `carrier` (including `epic.author`) accepts `solo|subagent`. **`parallel` is a flag (`on|off`), not a recipe:** it resolves OUTSIDE the recipe lattice, never degrades, and never reaches the planner. A silent slot takes its **computed default** — `solo` for `author`, `fold`, `execute` and `carrier` (placing either vehicle never flips a default; the subagent carrier is opt-in exactly as `delegated` is), `reviewed`/`solo` by readiness for `review`, and `on` for `parallel`.

**The configured-recipe line (`--active-line`, read-only).** `node ${CLAUDE_SKILL_DIR}/tools/recipes.mjs --active-line` prints exactly **one** machine-composed line: the **CONFIGURED** recipe of every activity/slot, resolved from the target project's `docs/ai/orchestration.json` (read from the current directory) + live readiness — each slot with its source (configured vs computed default), its degradation stated, and its dispatched wrapper set — explicitly contrasted with the readiness **recommendation** (which is informational; the configured recipes are what runs). Paste it verbatim: it fills the session-start discovery step (the deployed `agent_rules.md` §1.1) and the handover "Active recipes:" slot; `set-recipe` echoes the same line after every successful write. A malformed config fails loud (exit 1), never a silent fallback.

On the status line, `ready` for a bridge means wired where the project settings enable the sandbox: the segment ` · sandbox: <condition>` states `ready means wired` where the host honors the settings sandbox keys when they enable it, `ready means installed` where they do not, or `unchecked — <reason>` when it cannot be judged. A ready bridge whose sandbox entries are missing shows `✗ not wired — <n> sandbox entr(ies) missing` (`✗ not wired (unused) — <n> sandbox entr(ies) missing` when no slot uses it) or `✗ unchecked — <reason>`. The recommended recipe stays the readiness one, its clause naming each ready bridge whose review surfaces are not wired (`not wired: <alias> (review)`) or unchecked; a bridge missing only its execution wrapper's entries shows in its cell and its not-wired line. After the recommended line, the recipes output lists one `not wired: <alias> — missing …; <condition>; <route>` line per such bridge and one `unchecked: <alias> — <reason>` line per unchecked bridge; the route is the chat yes of `/agent-workflow-kit upgrade` (once a slot uses an unused bridge for review).

**Invariants:** read-only · never runs a subscription CLI · never commits · the orchestrator executes the recipe via the bridge skills or the vehicle of the slot's role, not the kit.
